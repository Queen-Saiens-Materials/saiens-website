部署架構

Kamal 2 → GCP

自訂 Dockerfile 經 GCP Artifact Registry 部署至 GCP VM；DB 為 Cloud SQL。Production：system.saiens.tw（db saiens_production）；另有 staging 與隔離 training 環境。CI 已改 Mac Mini self-hosted runner，workflow 改造待接手。

資料規模

營運資料量

銷售訂單 11,544 筆（已確認 3,591 筆／NT$3.53 億）、CRM 商機 11,083 筆、客戶 3,056、產品模板 1,959、會計傳票 13,782 筆（2022-03 至 2026-07）。已知資料債：草稿單 7,690 筆、供應商主檔僅 2 筆、進項傳票僅 2 筆。

已上線防護

稽核與分權

OCA auditlog 已上線 production（6 條規則覆蓋 account.move、payment、partner、sale／purchase order、users）；agent 服務帳號分權（agent-readonly／agent-writer）；每日 07:00 日結對帳 cron（AR 帳齡必濾 posted）。

最優先技術債

Guarded Executor

XML-RPC 腳本預設仍用 admin 帳號，guarded executor 尚未常態化——這是目前最優先的技術債。另有教訓：小額 PO 自動確認規則因 99.6% 誤判（draft PO 實為報價副產品）全數廢除，自動化必須先懂業務語意。

為什麼現在動 Odoo

2026-08-01 玉禮／山恩分治生效。山恩收斂為設計師＋個人業主雙主引擎、11 人穩態底盤——系統必須撐起「小團隊 × 高人均」的營運模式。

  • Odoo 是唯一事實來源（SSOT）

    2026-07-29 定案：一切財會與營運資料以 Odoo 為唯一 SSOT，外部表格只能是匯入來源或唯讀展示層。成長系統的實驗數據一律由 agent 自 Odoo（posted）自動採集，不接受人填——pipeline 灌水 3,895 萬是前車之鑑。

  • 分治後的系統邊界

    維持一套 AIOS，主體定錨山恩；vault 與 registry 以 Saiens／QSM玉禮／Shared 三種 entity 劃分，玉禮營運明細不進山恩生態。2026-08-03 進一步定案：Odoo 資料層由多公司邏輯分區走向物理分離——舊 17 db 留玉禮作中控／庫存，山恩新建 19.4 實例（見下方定案節）。

  • AIOS 成熟度是 175 萬的前提

    增員鐵律：必須先證明 Agent 無法承接該職能才可加人。人均從 89 萬走向 175 萬，依賴 AIOS 從 L2（主動推播）走到 L3（對話助理）、L4（受監督自主）——Odoo 資料品質與 API 層是全部的地基。

    • AIOS 架構中的 Odoo

    五層控制平面：Odoo 是「正式企業資料層」，上有治理與知識層、旁有 agent 調度層。所有 Odoo 開發都必須在這個框架內落位。

    山恩 Odoo 19.4 新建（已定案）

    2026-08-03 Michael × 蘇Sir 共識定案：藉分治一次把山恩 ERP 做到位。山恩 db 獨立、新建 Odoo 19.4 AI Native 實例（準備未來 Odoo 20）；舊 17 db 保留給玉禮作中控／庫存。目標：支撐 10 位業務 5 倍業績成長。

    玉禮 · Odoo 17（現行 db）中控／庫存續用；資料債（草稿單 7,690、堆積商機 4,089）就地歸檔，不搬家
    跨實例整合介面事件流／API 同步層：山恩下單 → 玉禮工程進度與庫存回報 → 山恩驗收開票（取代原同 db 鏡射設計）
    山恩 · Odoo 19.4（新建）七大模組域：客戶資料／商機管理／訂單管理／採購管理／工程進度及庫存追蹤／財會帳務／人事資料 — 一切以山恩業務策略規劃

  • Greenfield，不走 in-place 升級

    不用 OpenUpgrade 17→18→19 逐版升級，直接新建 19.4 實例＋選擇性資料遷移。紅利：資料債留在玉禮 db 歸檔，山恩主資料（客戶／產品／價格表／未結案件）清洗後入新實例，從乾淨 schema 起步。AI Native 是出廠標配而非事後補課：agent 分權、guarded executor、auditlog、API-first、事件流第一天內建。

  • 三項配套決策（已拍板）

    ① 8 月財會落點＝現行 17 db 先完成鼎新承接與首次月結（月結不能斷），19.4 並行建置；② 切換基準日＝2026-10-01（8–9 月建置＋平行驗證，Q4 初配合 11 人穩態底盤）；③ 授權路線＝Community＋OCA 重拼（延續 17 模式、零授權費）。原未決事項「玉禮在此 db 的處置」「Community vs Enterprise」同步結案。

  • Blocking 前置：模組 19 相容盤點

    山恩新實例要能開票——l10n_tw、電子發票（ezpay／amego／ecpay）、台灣票據 yc_note_*_tw、常用 OCA 模組的 Odoo 19 相容版必須逐一確認；沒有 19 版的要改寫或換方案。saiens_react_api 前端層須對 19 重新對接（ORM／OWL 架構差異）。此項升為 W1–W2 最高優先。

  • 切換路徑與回退

    8 月：staging 起機＋blocking 盤點＋建置藍圖與資料遷移計畫書。9 月：主資料遷移實跑＋雙軌平行期（17 記帳、19.4 影子驗證）＋跨 db 介面聯調。10-01 正式切換——沿用 Kamal 藍綠部署與備份機制，production 切換須具名核准，平行期即回退方案。

    • 治理紅線

    所有 Odoo 開發（含升級）不可妥協的邊界。2026-07-31 曾有兩個 subagent 因無法驗證授權而拒絕 production 寫入——防護設計已被實證有效。

    寫入需具名核准

    財務記錄、發票、付款、定價、HR 與一切 Odoo 寫入，執行前須具名人工核准；AI 不可自主執行財務操作。

    稽核不可修改

    任務啟動與完成都寫稽核記錄，write-once append-only；財務／人事保存至少 24 個月。

    驗證不自驗

    agent 產出須由第二 agent 或人工抽核；verifier 未過不得標記 deployment-ready。

    範疇宣告

    所有 agent 部署前須宣告 scope manifest；自我擴展範疇即停權。

    單次生成原則

    提示詞執行前必須完整規格化：一個 prompt、一份完整產出，不做迭代式修補。

    專案邊界

    報價計算、SO 建立、對客定價與折扣屬外部 Quote Agent 專案；Odoo Agent Farm 必須阻擋這類請求。

    關鍵 1

    W1–W2 不能拖的兩件事

    財會人選與截轉基準日卡住整條 P1（Planner 的球）；台灣本地化模組的 19 相容盤點卡住整條 19.4 線（Executor 的球）。兩條線第一、二週必須同時出手。

    關鍵 2

    驗收標準前置

    契約介面用 OpenSpec：每個 change 動工前，驗收條件已寫死在規格裡。「說完成」不算完成——staging 實跑＋Planner 或第二 agent 驗過才算。

    關鍵 3

    UI/UX 短循環

    規格 → 實作 → 截圖驗收。每個畫面出 staging 截圖就地審，不等整包完成，縮短來回。

    協作節奏：每日非同步 standup（Discord workbench 或 LINE，三句話：昨天完成／今天做／卡在哪）＋每週五 60 分鐘驗收會——staging 實跑通過，才排 production（具名核准）。

    給蘇Sir 的接球點

    四件事，依優先序，已一一對應上方 W1–W4 的技術線。定案內容已入 vault 決策紀錄（saiens-erp-odoo19-split-2026-08）。

    1. 模組 19 相容盤點（blocking）

      l10n_tw、電子發票（ezpay／amego／ecpay）、台灣票據、常用 OCA 模組逐一確認 Odoo 19 相容版；沒有 19 版的提改寫或替代方案。19.4 線的成敗閘門。

    2. Guarded executor 常態化

      把 XML-RPC 腳本從 admin 帳號全面收斂到 agent-readonly／agent-writer 分權＋核准閘——17 db 立即生效，同套設計直接成為 19.4 出廠規格。

    3. 19.4 staging 起機＋跨 db 介面

      新實例部署架構（沿用 Kamal 藍綠模式）、persistent audit store 落新實例（OpenSpec 23 項規格已備）、玉禮工程／庫存 → 山恩的事件流／API 同步層設計。

    4. 建置藍圖＋資料遷移計畫書

      W4 交付：主資料遷移規則、10-01 切換程序、9 月平行期規則與回退方案；CI workflow（Mac Mini runner）一併定案。

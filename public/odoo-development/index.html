部署架構

Kamal 2 → GCP

自訂 Dockerfile 經 GCP Artifact Registry 部署至 GCP VM；DB 為 Cloud SQL。Production：system.saiens.tw（db saiens_production）；另有 staging 與隔離 training 環境。CI 已改 Mac Mini self-hosted runner，workflow 改造待接手。

已上線防護

稽核與分權

OCA auditlog 已上線 production（6 條規則覆蓋 account.move、payment、partner、sale／purchase order、users）；agent 服務帳號分權（agent-readonly／agent-writer）；每日 07:00 日結對帳 cron（AR 帳齡必濾 posted）。

最優先技術債

Guarded Executor

XML-RPC 腳本預設仍用 admin 帳號，guarded executor 尚未常態化——這是目前最優先的技術債。另有教訓：小額 PO 自動確認規則因 99.6% 誤判（draft PO 實為報價副產品）全數廢除，自動化必須先懂業務語意。

為什麼現在動 Odoo

2026-08-01 玉禮／山恩分治生效。山恩收斂為設計師＋個人業主雙主引擎、11 人穩態底盤——系統必須撐起「小團隊 × 高人均」的營運模式。

  • Odoo 是唯一事實來源（SSOT）

    2026-07-29 定案：一切財會與營運資料以 Odoo 為唯一 SSOT，外部表格只能是匯入來源或唯讀展示層。成長系統的實驗數據一律由 agent 自 Odoo（posted）自動採集，不接受人填——pipeline 灌水 3,895 萬是前車之鑑。

  • 分治後的系統邊界

    維持一套 AIOS，主體定錨山恩；vault 與 registry 以 Saiens／QSM玉禮／Shared 三種 entity 劃分，玉禮營運明細不進山恩生態。不做 repo 物理分家，交割後再議。玉禮實業在同一 db 的拆分後處置，是待決事項之一。

  • AIOS 成熟度是 175 萬的前提

    增員鐵律：必須先證明 Agent 無法承接該職能才可加人。人均從 89 萬走向 175 萬，依賴 AIOS 從 L2（主動推播）走到 L3（對話助理）、L4（受監督自主）——Odoo 資料品質與 API 層是全部的地基。

    • AIOS 架構中的 Odoo

    五層控制平面：Odoo 是「正式企業資料層」，上有治理與知識層、旁有 agent 調度層。所有 Odoo 開發都必須在這個框架內落位。

    Odoo 19 升級評估

    誠實起點：vault 目前沒有既定的大版升級計畫。這一節是「評估議程」，不是已核定的 roadmap——正是要與蘇Sir 討論定案的部分。

  • 為什麼考慮升級

    17 → 19 帶來 ORM 與前端框架演進、原生 AI 功能與長期支援週期。但現行 Enterprise 缺口已由 OCA／第三方模組補齊（票據、電子發票、資產、預算、tier validation），「短期不需升 Enterprise」已是既定評估結論——升 19 的動機需要獨立論證，不能與 Enterprise 議題混談。

  • 主要風險：模組相依

    OCA 模組升級綁大版（此顧慮已寫入月結機制設計，因此鏡射方案改用排程腳本影子跑）；三家電子發票模組（amego／ecpay／ezpay）、台灣票據模組、自訂 addons 與 saiens_react_api 都要逐一確認 19 相容版本或改寫成本。這是升級評估書的核心工作量。

  • 前置條件（未完成不啟動升級）

    ① P1–P2 財會地基完成且跑過至少兩次乾淨月結；② 四個未決人工決策點結案（採購／應付截轉基準日、玉禮在此 db 的處置、Community vs Enterprise、帳簿去重與鎖帳日）；③ 資料清理 backlog 第一批完成——帶著 7,690 筆草稿單升級只是把債搬家。

  • 建議路徑

    2026 Q4 產出升級評估書（模組相依盤點＋成本估算）→ training／staging 環境以 OpenUpgrade 路徑演練（17→18→19 逐版）→ 驗收自訂模組與 agent API 層 → 2027 擇機切換。全程沿用現有 Kamal 藍綠部署與備份機制，production 切換須具名核准。

    • 治理紅線

    所有 Odoo 開發（含升級）不可妥協的邊界。2026-07-31 曾有兩個 subagent 因無法驗證授權而拒絕 production 寫入——防護設計已被實證有效。

    寫入需具名核准

    財務記錄、發票、付款、定價、HR 與一切 Odoo 寫入，執行前須具名人工核准；AI 不可自主執行財務操作。

    稽核不可修改

    任務啟動與完成都寫稽核記錄，write-once append-only；財務／人事保存至少 24 個月。

    驗證不自驗

    agent 產出須由第二 agent 或人工抽核；verifier 未過不得標記 deployment-ready。

    範疇宣告

    所有 agent 部署前須宣告 scope manifest；自我擴展範疇即停權。

    單次生成原則

    提示詞執行前必須完整規格化：一個 prompt、一份完整產出，不做迭代式修補。

    專案邊界

    報價計算、SO 建立、對客定價與折扣屬外部 Quote Agent 專案；Odoo Agent Farm 必須阻擋這類請求。

    給蘇Sir 的接球點

    四件事，依優先序。定案後回寫 vault 決策紀錄。

    1. Guarded executor 常態化

      把 XML-RPC 腳本從 admin 帳號全面收斂到 agent-readonly／agent-writer 分權＋核准閘——最優先技術債，也是 L4 的前提。

    2. Persistent task／audit store

      OpenSpec 規格已備（23 項任務未開工）：任務與稽核事件落地 Postgres，解決 in-memory 重啟即失的問題。

    3. CI workflow 接手

      Mac Mini self-hosted runner 已上線，GitHub Actions workflow 改造待定案（build、測試、Kamal 部署管線）。

    4. Odoo 19 升級評估書

      共同定義評估範圍與時點：模組相依盤點、OpenUpgrade 演練計畫、成本與風險估算，目標 2026 Q4 產出。
